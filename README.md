# OAHT-Bench

**A survey and benchmark for offline ad-hoc teamwork (AHT).**

Ad-hoc teamwork asks an agent to coordinate with partners it has never trained
with. *Offline* AHT asks it to learn that from a fixed dataset, with no
interaction. The problem is well studied, but incomparably: every method brings
its own environments, its own teammate populations, its own data-collection
recipe, and its own metrics — so no two of the frequently-cited methods have ever
been run head-to-head. OAHT-Bench fixes the protocol so they can be.

> **Status: pre-release, under active development** (targeting AAMAS 2027). The
> **LBF 12×12** track is the reference environment and the one that runs end to
> end today; Hanabi and Overcooked-v2 are scaffolded but not yet tuned. Configs
> and APIs may still change.

## What's in the benchmark

- **Environments** — Level-Based Foraging (12×12), Hanabi, and Overcooked-v2.
- **Teammate generators** — FCP, CoMeDi, BRDiv, and L-BRDiv (plus AD-RPG on LBF),
  trained in-house so the populations behind every dataset are controlled and
  reproducible rather than inherited.
- **Offline baselines** on one shared Decision-Transformer backbone, so measured
  differences trace to the teammate-modeling mechanism rather than to per-method
  offline-conversion choices. Implemented today: **BC**, **LIAM**, **MeLIBA**,
  **TAO**, **OMIS**. On the roadmap: TAGET, plus a random floor and a
  privileged-teammate oracle ceiling.
- **Datasets** — D4RL-style regimes over an AHT-specific schema, seated across a
  *pooled* best→worst response spectrum and stored as memory-mapped Flashbax
  Vaults.

The scope, schedule, and protocol live in `docs/offline_aht_benchmark_project.md`;
the per-method extraction (architectures, losses, hyperparameters) in
`docs/baseline_specs.md`; and the per-environment tuning record — a contribution
in its own right — in `docs/tuning_record.md`.

## Install

Uses [uv](https://docs.astral.sh/uv/). Python 3.11; JAX 0.5.3 (CUDA on Linux,
CPU on macOS).

```bash
uv sync --extra dev
uv run python -m pytest tests/ -q      # ~215 tests
```

## Running experiments

Every step of the pipeline is a single JSON config run through one CLI:

```bash
uv run oaht-bench config=<path-to-config>.json
```

Configs are laid out **environment-first**, one directory per step
(`configs/<env>/<step>/<name>.json`), so an environment's full path reads top to
bottom. For LBF 12×12:

```bash
# 1. Teammate generation — train each generator's population
uv run oaht-bench config=configs/lbf_12x12/teammate_gen/fcp.json      # + comedi, brdiv, lbrdiv

# 2. Pooled cross-play — score every (ego, teammate) pair across all four populations
uv run oaht-bench config=configs/lbf_12x12/crossplay/pooled.json

# 3. Dataset collection — roll out the ε-sampled response-quality spectrum
uv run oaht-bench config=configs/lbf_12x12/data_collection/pooled.json

# 4. Training — train an offline baseline, evaluated against the population
uv run oaht-bench config=configs/lbf_12x12/training/bc.json           # or liam / meliba / omis / tao
```

Each step writes to `results/<job_type>/<label>-<config-hash>/`. Every config is a
validated Pydantic model whose content hash names its run directory, so a dataset
or checkpoint is always traceable to the exact configuration that produced it. The
teammate-generation configs are generated by `scripts/gen_teammate_configs.py`
(the source of truth); the rest are hand-written.

## Contributing a teammate population

Populations are the shared input to every downstream step, so growing the
benchmark to a new environment or layout starts here. The workflow is **train each
generator, then release the adopted checkpoint** into the durable `populations/`
tree that the pipeline reads.

Teammate generation is compute-heavy — run it on a GPU (Linux); a single generator
is on the order of hours. `results/` is gitignored (it holds every attempt);
nothing there is shared until you release it.

### 1. Train

Configs live at `configs/<env>/teammate_gen/<generator>.json`. Train each of the
four generators for your environment:

```bash
for gen in fcp comedi brdiv lbrdiv; do
  uv run oaht-bench config=configs/<env>/teammate_gen/$gen.json
done
```

Each run writes `results/teammate_generation/<label>-<hash>/` — the checkpoint,
`job.json` (the exact config), and a post-training cross-play evaluation.

> **Configs are generated, not hand-edited.** `scripts/gen_teammate_configs.py` is
> the source of truth: tuned per-environment hyperparameters live there (with a
> comment saying why), and hand edits are lost on the next
> `uv run python scripts/gen_teammate_configs.py` (add `--wandb <project>` to log to
> Weights & Biases). A **new** environment or layout needs its own tuned
> per-generator hyperparameters — see *Tuning* below.

### 2. Release

When a run is good, publish its checkpoint into `populations/`:

```bash
uv run python scripts/release_population.py \
    results/teammate_generation/<your-run> --dest populations
# -> populations/<env>/<generator>/
```

`populations/` is the git-tracked record of the *one adopted* checkpoint per
`(environment, generator)` — distinct from the gitignored `results/`. The release
copies `job.json` in beside the checkpoint, so the population can never be
separated from the config that produced it (a released directory is itself a valid
run dir). It's one slot per environment×generator; pass `--force` to replace one
after re-tuning. Commit the new `populations/<env>/` entries.

Once all four generators are released for an environment, its populations feed the
pipeline above — build the pooled cross-play matrix, then collect datasets.

### Tuning a new environment or layout

The shipped configs are tuned for the environments above; a new one needs its own
hyperparameters. Tune each generator with `scripts/sweep.py`, which materializes a
grid as one config per cell — each with its own hash and run directory, so a cell
can be re-run or cited in isolation, and an invalid cell fails at generation rather
than after it's queued:

```bash
# 1. Expand a grid over a base config into configs/sweeps/<name>/
uv run python scripts/sweep.py generate \
    --base configs/<env>/teammate_gen/brdiv.json --name brdiv_<env>_xpw \
    --set generator.cross_play_weight=0.005,0.05,0.5 \
    --set generator.ppo.learning_rate=1e-4,5e-4

# 2. Train every cell (--jobs runs N in parallel; finished cells are skipped)
uv run python scripts/sweep.py run configs/sweeps/brdiv_<env>_xpw --jobs 2

# 3. Compare cells — self-play and cross-play returns, reported separately
uv run python scripts/sweep.py collect --sweep configs/sweeps/brdiv_<env>_xpw

# 4. Re-score finalists from their checkpoints (no retraining) at more episodes
uv run python scripts/sweep.py rescore results/teammate_generation/<cell> --episodes 100
```

`collect` keeps self-play and cross-play separate on purpose: the diversity-seeking
generators trade them off, and a single score hides the degenerate corner where
cross-play is low only because the population is incompetent. Once a cell wins, fold
its values back into `scripts/gen_teammate_configs.py` (with a comment saying why),
regenerate, then train and release as above — and write up what the sweep concluded,
**and what it couldn't**, in `docs/tuning_record.md`. That record is a benchmark
contribution, not an appendix.

## Repository layout

```
src/oaht_bench/
  configs/        Pydantic config models + environment presets
  envs/           environments (LBF, Overcooked, Hanabi)
  teammate_gen/   FCP / CoMeDi / BRDiv / L-BRDiv / AD-RPG
  population/     pooled cross-play, loading, scoring
  dataset/        collection, ε sampler, Flashbax Vault storage, windowing
  models/         shared network architectures (Decision-Transformer backbone + agents)
  offline/        offline baselines (trainers + losses)
  common/         logging, vmapped rollouts
configs/<env>/<step>/   experiment configs (environment-first)
docs/                   project plan, per-paper baseline specs, tuning record
tests/{unit,integration}/
LICENSES/               upstream license texts for absorbed code
```
